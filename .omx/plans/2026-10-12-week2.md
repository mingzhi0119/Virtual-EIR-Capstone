Improve the usefulness of the coaching and produce an inspectable evaluation of the next prototype. Keep the English interface, explicit founder confirmation, and local fictional-data boundary.

## Proposed steps and outputs

1. **Monday: incorporate faculty feedback and confirm responsibilities.** Review the user journey, profile, and coaching framework. Record feedback as accepted changes, open questions, or deferred work. Confirm who owns product research, implementation, evaluation, and documentation. Do not invite contributors until Mingzhi approves the actual accounts and permissions. Output: a prioritized Week 2 backlog and responsibility list. References: docs/IMPLEMENTATION_CHECKLIST.md, R9 and R13.

2. **Tuesday: improve the coaching questions.** Review questions that imply the founder's assumption is correct or ask hypothetical willingness to pay. Revise the coaching instructions toward recent purchases, existing alternatives, and neutral follow-ups. Keep explicit sample-size limitations and distinguish proposed actions from completed work. Output: revised instructions and a before/after example with a documented limitation. References: deliverables/2026-10-08/Speaker-Script-v3.md, slides 4–7 and "What is the most important weakness today?"; docs/LOCAL_RUN.md, section 6. Do not claim prompt changes guarantee model compliance.

3. **Wednesday: refine intake and prepare focused Ain questions.** Check whether the profile captures information needed to change the advice, including venture stage, target customer, reported evidence, and feasible action size. Implement only the highest-priority confirmed intake gap. Draft a request for an approved mentoring template or anonymized example, subject to permission. Output: revised intake specification and a short feedback package with the working example. Sponsor contact and expert review require coordination and are not promised to occur this week. References: docs/ROADMAP.md, sections 4–5; docs/IMPLEMENTATION_CHECKLIST.md, R10.

4. **Thursday: run a small controlled evaluation.** Use three fictional cases covering no evidence, incomplete action, and new evidence contradicting an assumption. Compare general GOAT chat with Virtual EIR using the same model and matched confirmed facts. Record how each system receives the facts so a context advantage is not mislabeled as superior model reasoning. Run each case twice per configuration: 12 two-session trajectories in total. Score question relevance, assumption/evidence distinction, action feasibility, memory accuracy, and response to new evidence on a defined 1–5 scale. Preserve outputs and failure notes. Output: a comparison table, rubric, and reproducible fictional records. References: docs/ROADMAP.md, section 6; docs/IMPLEMENTATION_CHECKLIST.md, R11. These are internal ratings, not expert validation.

5. **Friday: fix the highest-impact observed failures and prepare the review.** Run the relevant regression tests, check persisted corrections and planned/completed counts, and present one before/after case. Update the demo and report any remaining critical issue. Output: revised local prototype and a short progress report with evidence, unresolved issues, and the next decision. References: docs/IMPLEMENTATION_CHECKLIST.md, R5–R7 and R21; docs/ROADMAP.md, section 8.

Throughout the week, use a separate test database and local service configuration for experiments. Preserve the clean faculty-demo database. Do not simply rerun scripts that write into it. Reference: docs/archive/2026-10-08-demo-cleanup-and-script.md, R22.

## Acceptance criteria and verification

- A backlog identifies priorities and proposed owners. Unconfirmed roles and external dependencies remain visibly marked.
- Each accepted change links to a feedback item or an observed failure.
- Coaching changes include at least one before/after example. Record any remaining leading or hypothetical question instead of marking it fixed solely because the prompt changed.
- All 12 evaluation trajectories have inputs, model/configuration, supplied context, outputs, and rubric scores. Explain whether the two runs reveal inconsistent behavior.
- Deterministic tests confirm saved corrections, correct venture/session association, and distinct planned/completed counts. Review all evaluation outputs for invented completed actions or evidence claims. Treat any such occurrence as a critical unresolved failure.
- The existing faculty-demo venture and its saved sessions remain unchanged by automated evaluation.
- The end-of-week report separates implemented changes, internally tested behavior, and feedback still awaiting an expert.

## Risks and boundaries

- **Faculty or Ain feedback is unavailable:** continue the fictional-case evaluation and keep unconfirmed sponsor-specific choices provisional.
- **Too much work for one week:** prioritize coaching changes and evaluation over new features. Defer optional intake implementation if it threatens the comparison and review deliverables.
- **Prompt improvements appear inconsistent:** retain raw outputs and failure examples. Do not claim reliable coaching from a favorable single run.
- **Test data accumulates in the live demo:** isolate evaluation data before running experiments.
- **Shared access creates exposure:** no public or LAN deployment and no real sensitive founder data. Authentication and dependency remediation remain explicit gates (docs/IMPLEMENTATION_CHECKLIST.md, R14–R16).
- **Cloud costs expand scope:** continue with local Ollama. Prepare a provider/usage/spending-cap proposal only if evaluation shows a need, with approval before paid calls (docs/IMPLEMENTATION_CHECKLIST.md, R12).

Voice, fine-tuning, automatic profile extraction, and a large knowledge base are deferred for this week. This planning turn does not implement changes, contact Ain, invite contributors, or alter repository permissions.
